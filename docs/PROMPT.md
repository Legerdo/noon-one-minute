# 장비와 시간을 읽는 2D Pixel Art RPG

## Claude Opus 5.5 자율형 원샷 게임 제작 프롬프트 — 독립 실행판

완성된 **2D Pixel Art 전술 RPG**를 실제로 제작하라.

이 문서 하나만으로 기획, 구현, 아트, UI, 사운드, 밸런스, 테스트, 실행 검증까지 끝낼 수 있어야 한다. 별도의 원본 게임, 참고 프로젝트, 외부 문서, 과거 대화가 없어도 된다.

플레이어에게 보이는 기본 언어는 **한국어**다.

계획서나 기술 데모가 아니라, 처음부터 끝까지 플레이 가능한 작은 완성형 게임을 목표로 한다.

# 1. 핵심 경험

게임의 중심은 **상대가 무엇을 언제 할지 읽고, 지금 준비할 장비를 선택하여 공격·방어·속도의 교환관계를 이용하는 1대1 전술 전투**다.

핵심 감각은 다음과 같다.

> 빠른 장비로 먼저 행동하고, 위험한 순간에는 방어적인 장비로 전환하며, 상대가 긴 행동이나 취약한 자세를 선택했을 때 강한 공격으로 보상받는다.

플레이어는 반사 신경보다 **판단과 장비 선택**으로 승리해야 한다.

전투에서는 최소한 다음 세 값이 명확하게 읽혀야 한다.

- **Effect**: 행동 완료 시 발생하는 공격, 회복, 지연 등의 결과

- **Defense**: 해당 행동을 준비하는 동안 적용되는 방어 성능

- **Wait**: 행동 완료까지 필요한 논리적 시간

이 세 값의 관계에서 전략이 나오게 하되, 필요하면 소수의 특수 효과를 추가할 수 있다.

전체 플레이는 최소한 다음 흐름을 가진다.

**탐험 → 발견 → 장비 선택 → 전투 판단 → 보상과 성장 → 더 어려운 문제 → 마지막 도전 → 결말**

전투 화면만 있는 시뮬레이터도, 전투가 빈약한 탐험 게임도 만들지 않는다.

# 3. 구현 전 필수 규칙 점검

실제 구현에 들어가기 전에 먼저 이 문서의 전투·성장·진행 규칙을 검토하라.

목적은 문서를 다시 길게 요약하는 것이 아니라 **구현 중 서로 다른 해석이 생길 수 있는 지점을 제거하는 것**이다.

먼저 짧은 `DESIGN_LOCK.md` 또는 동등한 내부 설계 문서를 만든다.

최소한 다음을 확정한다.

1. 핵심 플레이 루프

2. 전투 상태와 상태 전이

3. 행동 확정과 취소 가능 여부

4. Wait 감소 시점

5. Defense 적용 시점

6. 피해와 회복 계산

7. 동률 처리

8. 사망 판정 시점

9. 적의 다음 행동 결정 시점

10. 적 AI가 참조할 수 있는 정보

11. 특수 효과의 적용·종료·중첩 순서

12. 장비 구성과 성장 방식

13. 패배·재도전·보상 중복 규칙

14. 저장 범위

15. 입력 확정과 연타 방지

16. 연출과 실제 판정의 경계

아래 본문에서 이미 확정한 규칙은 다시 해석하지 말고 그대로 사용한다.

본문이 허용한 자율 영역은 스스로 합리적인 기본안을 선택해 확정한다.

## 사용자 확인이 필요한 경우

다음 세 조건을 모두 만족할 때만 사용자에게 질문한다.

- 둘 이상의 해석이 모두 자연스럽고,

- 선택에 따라 핵심 게임 경험이나 사용자의 의도가 실질적으로 달라지며,

- 이 문서의 기준만으로 어느 쪽을 선택할 근거가 없다.

색상, 이름, 장비 개수, 맵 크기, 세부 수치, 일반적인 코드 구조 같은 제작 판단은 묻지 말고 스스로 결정한다.

질문이 필요한 경우에는 구현을 시작하기 전에 **선택지와 각 차이를 짧게 제시하고 필요한 결정만 묻는다.**

그 외에는 스스로 확정하고 제작을 계속한다.

구현 도중 새로운 모순이 발견되면 임시 예외 코드를 덧붙이지 말고 먼저 `DESIGN_LOCK`과 규칙을 정리한 뒤 코드와 테스트를 함께 수정한다.

# 4. 전투 핵심 계약

## 4.1 장비 선택이 행동 선택이다

플레이어는 전투 중 하나의 장비 또는 행동을 확정한다.

각 행동은 최소한 다음 값을 가진다.

```text

id

name

kind

effect

defense

wait

```

필요한 경우 다음과 같은 속성을 추가할 수 있다.

```text

damageType

penetration

pierce

heal

delay

buff

resourceCost

specialRule

animation

sound

```

행동을 확정하면 즉시 `currentAction`이 된다.

공격이나 회복 효과는 이 순간 발생하지 않는다.

**Wait가 0이 되었을 때 행동 효과가 해결된다.**

---

## 4.2 행동 확정 후에는 중도 교체하지 않는다

한 번 확정한 행동은 완료될 때까지 유지한다.

기본 규칙에서는 다음을 허용하지 않는다.

- 준비 중 다른 장비로 교체

- 적이 먼저 행동했다는 이유로 준비 취소

- 미리보기로 현재 행동 변경

- 애니메이션 스킵으로 행동 완료

- 연타로 두 행동 동시 예약

행동 취소 시스템을 별도로 만들지 않는다.

향후 정말 필요하다면 취소 자체를 명시적인 행동 규칙으로 설계하고 비용·Wait·UI·AI·테스트까지 함께 정의해야 한다.

---

## 4.3 양측의 시간은 독립적이다

플레이어와 적은 각각 자신의 `currentAction`과 `remainingWait`를 가진다.

기본 사건 진행:

```text

Δt = min(playerRemainingWait, enemyRemainingWait)

playerRemainingWait -= Δt

enemyRemainingWait -= Δt

logicalTime += Δt

```

먼저 0이 된 행동을 해결한다.

행동하지 않은 쪽의 남은 Wait는 보존한다.

예:

```text

Player Wait = 3

Enemy Wait = 9

```

플레이어 행동이 끝난 뒤 적의 남은 Wait는 6이다.

적이 먼저 행동하더라도 플레이어의 진행 중 행동은 그대로 유지된다.

---

## 4.4 플레이어 선택 대기 중에는 시간이 흐르지 않는다

플레이어가 새 행동을 고르는 동안 논리적 전투 시간은 정지한다.

다음은 전투 결과에 영향을 주지 않는다.

- 실제 고민 시간

- 마우스 이동

- 장비 설명 열람

- 포커스 이동

- 프레임 속도

- 애니메이션 길이

- 연출 스킵

- 사운드 재생

즉, 빠른 클릭 능력이 아니라 **선택의 내용**이 중요하다.

---

## 4.5 현재 준비 중인 장비가 현재 방어다

장비를 확정하는 순간 그 행동의 Defense가 적용된다.

예:

```text

활

Effect 7

Defense 0

Wait 3

철방패

Effect 0

Defense 15

Wait 7

```

활 준비 중 피격되면 Defense 0이다.

철방패 준비 중 피격되면 Defense 15다.

철방패 행동이 끝나고 활을 확정하면 그 순간부터 Defense 0이다.

이전 방패의 방어가 숨겨진 지속 버프로 남지 않는다.

다음 세 상태를 UI와 로직 모두에서 구분한다.

```text

현재 확정 행동

장비 미리보기

행동 없음

```

미리보기는 실제 Defense나 상태를 바꾸지 않는다.

# 5. 행동 해결 순서

## 5.1 플레이어 행동만 먼저 완료된 경우

1. 플레이어 행동 효과를 해결한다.

2. 적 사망 여부를 확인한다.

3. 적이 사망했으면 즉시 승리 처리한다.

4. 플레이어의 완료 행동을 해제한다.

5. 적의 현재 행동과 남은 Wait는 그대로 둔다.

6. 플레이어에게 다음 행동 선택권을 준다.

7. 선택 중 논리 시간은 흐르지 않는다.

---

## 5.2 적 행동만 먼저 완료된 경우

1. 적 행동 효과를 해결한다.

2. 플레이어 사망 여부를 확인한다.

3. 플레이어가 사망했으면 즉시 패배 처리한다.

4. 적의 완료 행동을 해제한다.

5. 적의 다음 행동을 즉시 결정하고 공개한다.

6. 새 적 행동의 Wait를 설정한다.

7. 플레이어의 기존 행동과 남은 Wait는 그대로 유지한다.

8. 플레이어에게 새 장비 선택권을 주지 않는다.

9. 시간 진행을 계속한다.

즉, 적이 여러 번 빠르게 행동하는 동안 플레이어의 느린 공격이 계속 준비될 수 있다.

---

## 5.3 동률

기본 규칙은 **플레이어 우선**이다.

양쪽 `remainingWait == 0`이면 다음 순서를 사용한다.

1. 플레이어 행동을 먼저 해결한다.

2. 적 사망 여부를 즉시 확인한다.

3. 적이 죽었으면 전투를 종료하고 적의 완료 행동은 실행하지 않는다.

4. 적이 살아 있으면 플레이어의 완료 행동만 해제한다.

5. 적의 현재 행동과 `remainingWait = 0`을 그대로 유지한다.

6. 플레이어에게 새 행동 선택권을 준다.

7. 플레이어가 새 행동을 확정하면 그 장비의 Defense가 즉시 적용된다.

8. 논리 시간을 진행시키기 전에 `remainingWait = 0`인 적 행동을 즉시 해결한다.

9. 이 즉시 적 행동 때문에 새 플레이어 행동의 Wait는 감소하지 않는다.

10. 플레이어 사망 여부를 확인한다.

11. 생존했다면 적의 다음 행동을 결정하고 공개한다.

12. 이후 정상 시간 진행으로 돌아간다.

따라서 다음 전술이 가능하다.

```text

동률

→ 플레이어 공격

→ 적 생존

→ 방패 선택

→ 추가 시간 없이 적 공격

→ 새 방패 Defense로 피해 계산

```

이 순서는 우연한 함수 호출 순서가 아니라 게임 규칙이다.

# 6. 사망과 행동 취소

HP가 0 이하가 되는 즉시 해당 캐릭터는 사망 상태가 된다.

사망 판정은 **각 행동 효과가 완전히 해결된 직후** 수행한다.

사망한 캐릭터는 이후 행동을 수행하지 않는다.

기본 규칙에서는 양측 피해를 미리 예약해 놓고 나중에 동시에 적용하지 않는다.

동률에서도 플레이어 선행 행동으로 적이 죽으면 적 행동은 취소된다.

회복, 흡혈, 반동 피해처럼 한 행동 안에서 여러 효과가 있다면 그 행동의 정의에 적힌 순서를 하나의 원자적 해결 과정으로 적용한 뒤 사망을 판정한다.

특수 행동이 이 규칙과 다른 사망 판정 시점을 필요로 한다면 구현 전에 명시적으로 정의한다.

# 7. 피해·회복·수치 규칙

기본 전투 수치는 정수로 관리한다.

기본 물리 피해:

```text

damage = max(0, attackEffect - defenderCurrentDefense)

```

방어 무시:

```text

damage = max(0, attackEffect)

```

회복:

```text

hp = min(maxHp, hp + healEffect)

```

HP는 0 미만이 되지 않게 한다.

신규 행동의 Wait는 최소 1이다.

이미 준비가 끝난 행동이 `remainingWait = 0`인 것은 정상 상태이며, 새 행동의 Wait 0과 혼동하지 않는다.

## 백분율 보정이 필요한 경우

가능하면 정수 기반 단순 규칙을 우선한다.

관통률 등 백분율이 꼭 필요하면 다음 순서를 기본으로 사용한다.

```text

effectiveDefense =

floor(defenderCurrentDefense × (100 - penetrationPercent) / 100)

damage =

max(0, attackEffect - effectiveDefense)

```

퍼센트 값은 0~100 범위로 제한한다.

다른 배율 효과를 추가한다면 구현 전에 다음을 `DESIGN_LOCK`에 적는다.

- 적용 순서

- 반올림 방식

- 중첩 방식

- 최소·최대값

부동소수점 오차나 함수 호출 순서에 따라 전투 결과가 달라지지 않게 한다.

# 8. Buff·Debuff·특수 효과 규칙

특수 효과를 추가할 수 있지만, 효과 하나마다 구현 전에 최소한 다음을 정의한다.

```text

발동 시점

대상

적용 시점

지속 조건

종료 시점

중첩 여부

중복 적용 방식

소비 조건

사망 시 처리

전투 종료 시 처리

UI 표시

AI가 알 수 있는 정보

```

이 중 하나라도 불명확하면 구현 전에 규칙을 정한다.

특수 효과는 전투를 풍부하게 만드는 데 필요한 만큼만 사용한다.

상태 아이콘과 설명을 읽어야만 기본 피해 결과를 이해할 수 있을 정도로 복잡하게 만들지 않는다.

---

# 9. 적 행동 결정과 정보 공개

적은 항상 하나의 확정된 현재 행동을 가진다.

적 행동은 플레이어가 읽을 수 있도록 최소한 다음 정보를 제공한다.

- 행동 이름 또는 명확한 시각적 의도

- 남은 Wait

- 공격인지 방어인지 등 핵심 성격

- 특별히 위험한 속성이 있다면 필요한 경고

## 적이 다음 행동을 정하는 시점

적은 자신의 현재 행동이 해결된 직후 다음 행동을 결정한다.

한 번 확정된 적 행동은 다음 적 행동 해결 시점까지 바뀌지 않는다.

## AI가 볼 수 있는 정보

적 AI는 다음과 같은 **실제 확정 상태**를 사용할 수 있다.

- 자신의 HP와 상태

- 플레이어 HP와 상태

- 플레이어가 실제 확정한 현재 행동

- 현재 Defense

- 직전 행동

- 전투 단계 또는 패턴 카운터

적 AI는 다음에 반응하지 않는다.

- 플레이어의 마우스 hover

- 장비 포커스

- 설명창 열람

- 취소된 미리보기

- 아직 확정되지 않은 선택

즉, AI가 플레이어 행동에 대응하는 설계라면 **확정된 행동만 보고 반응**한다.

랜덤 AI를 사용할 필요가 없다.

고정 순환, 조건 분기, 단계 패턴처럼 학습 가능한 구조를 우선한다.

---

# 10. 장비 설계

장비는 공격력 순으로 교체되는 선형 업그레이드 목록이 아니다.

서로 다른 문제 해결 역할을 가져야 한다.

예:

### 빠른 무기

```text

낮은 Effect

낮은 Defense

짧은 Wait

```

적의 긴 행동 사이에 여러 번 행동할 수 있다.

### 균형형 무기

```text

중간 Effect

중간 Defense

중간 Wait

```

안정적인 기본 선택이다.

### 중량 무기

```text

높은 Effect

낮거나 중간 Defense

긴 Wait

```

큰 피해를 주지만 준비 중 여러 차례 공격받을 수 있다.

### 가벼운 방패

```text

Effect 0

중간 Defense

짧은 Wait

```

위험을 빠르게 넘기고 다음 선택으로 돌아간다.

### 무거운 방패

```text

Effect 0

높은 Defense

긴 Wait

```

강한 공격을 막지만 공격 기회를 포기한다.

### 방어 우회 공격

높은 Defense를 준비한 적을 공략한다.

### 회복 행동

즉시 회복보다 Wait를 가지는 행동을 기본으로 고려한다.

안전한 시간 구간을 계산해야 한다.

이 목록은 예시이며 더 나은 역할을 창작해도 된다.

새 장비는 가능하면 기존 장비의 완전한 상위 호환이 아니라 **새로운 대응 방법**을 제공한다.

초반 장비도 후반 특정 상황에서 가치가 남도록 설계한다.

---

# 11. 장비 구성과 성장

전투에 가져갈 수 있는 장비 수는 무한하지 않게 한다.

정확한 슬롯 수는 전체 콘텐츠 규모에 맞춰 구현 전에 결정한다.

권장 범위는 **4~8개**다.

전투가 시작된 뒤 창고 전체를 자유롭게 꺼내지 못하게 한다.

성장은 캐릭터의 숫자를 무한히 키워 전투 판단을 무력화시키는 방향보다 **장비의 역할을 조금씩 강화하거나 새로운 선택을 열어 주는 방식**을 우선한다.

예:

- Effect 소폭 증가

- Defense 소폭 증가

- Wait 감소

- 특수 효과 해금

- 특정 장비의 역할 강화

Wait 감소는 행동 순서를 바꾸므로 반드시 실제 전투를 다시 검증한다.

성장 시스템의 구체적 형태는 자유지만 다음은 명확해야 한다.

- 자원 획득 조건

- 소비 시점

- 강화 한도

- 취소 처리

- 중복 클릭 처리

- 재도전 보상

- 이미 획득한 보상 재수령 여부

---

# 12. 적과 보스

적의 차이를 HP와 공격력만으로 만들지 않는다.

각 적은 서로 다른 전술 질문을 던져야 한다.

예:

- 짧은 Wait를 반복해 느린 무기를 압박

- 긴 강타로 공격 후 방어 전환을 유도

- 높은 Defense로 공격 방식 전환 요구

- 방어 우회 공격으로 방패 반복 견제

- 특정 행동 뒤 긴 빈틈 발생

- 체력 구간에 따라 읽을 수 있는 패턴 변화

모든 적이 같은 장비 반복으로 쉽게 해결되지 않게 한다.

반대로 설명 없는 단 하나의 정답만 강요하지 않는다.

보스는 별도의 규칙 게임이 아니라 지금까지 배운 원리를 더 깊게 조합하게 한다.

새로운 특수 규칙이 필요하다면 한 번에 너무 많은 예외를 추가하지 않는다.

---

# 13. 탐험과 진행

전투만 이어지는 메뉴 게임으로 만들 필요는 없다.

작은 공간이라도 직접 이동하고 발견하는 즐거움을 제공한다.

탐험에는 다음 중 게임에 맞는 요소를 조합한다.

- 적과의 조우

- 새로운 장비 발견

- 짧은 대화

- 환경 변화

- 지름길

- 비밀 공간

- 전투를 암시하는 단서

- 성장 선택

- 보스 접근 조건

무의미한 긴 이동과 반복 랜덤 인카운터는 피한다.

새 장비를 얻은 뒤 가까운 시점에 그 장비의 강점을 실험할 기회를 준다.

플레이어가 무엇을 해야 하는지 외부 설명 없이 이해할 수 있어야 한다.

---

# 14. 패배·재도전·보상

패배 후 빠르게 다시 시도할 수 있게 한다.

기본 재도전은 해당 전투 시작 직전의 유효 상태로 돌아간다.

패배 때문에 영구 자원이 계속 감소하여 진행 불가능해지지 않게 한다.

일회성 보상은 한 번만 지급한다.

완료한 전투를 반복할 수 있게 한다면 반복 보상 규칙을 명확히 정한다.

같은 전투를 재시작하거나 화면을 새로고침한다고 장비·경험치·아이템이 복제되지 않게 한다.

---

# 15. 저장

최소한 주요 진행, 획득 장비, 성장 상태를 저장한다.

기본 권장안은 **전투 사이의 안정된 상태를 저장**하는 것이다.

전투 도중 저장을 지원하지 않아도 된다.

만약 전투 중 저장을 지원한다면 다음 모든 논리 상태를 저장해야 한다.

- 양측 HP

- 양측 currentAction

- 양측 remainingWait

- Buff/Debuff

- AI 패턴 상태

- 전투 보상 처리 여부

- logicalTime

- 기타 승패에 영향을 주는 값

렌더러 객체, 애니메이션 진행률, 파티클 등은 권위 상태로 저장하지 않는다.

---

# 16. 전투 UI

주인공과 적이 실제로 마주 보는 장면을 중심에 둔다.

숫자 대시보드가 전투 장면보다 더 강하게 보이지 않게 한다.

최소한 다음 정보는 빠르게 읽혀야 한다.

- 양측 HP

- 현재 확정 행동

- 남은 Wait

- 현재 적용 Defense

- 플레이어가 선택 가능한 장비

- 적이 준비 중인 행동

- 중요한 특수 상태

다음 세 가지는 명확히 시각적으로 구분한다.

```text

실제 현재 상태

장비 미리보기

선택 확정 후 예상 결과

```

미리보기는 상태를 변경하지 않는다.

예측 UI는 실제 전투 규칙과 같은 순수 계산 경로를 사용한다.

확정되지 않은 미래 행동을 사실처럼 예측하지 않는다.

예:

```text

적 남은 Wait 0

→ 이 장비 확정 직후 적 공격

→ 예상 피해 4

```

처럼 지금 확실히 계산할 수 있는 범위만 보여준다.

---

# 17. 입력 규칙

마우스와 키보드 모두 사용 가능하게 한다.

기본 입력 예:

```text

이동: WASD / 방향키

확정·조사: Enter / Z

취소: Esc / X

```

정확한 키는 필요하면 조정할 수 있다.

한 번의 선택 창에서 하나의 행동만 확정되게 한다.

다음을 방지한다.

- 더블 클릭으로 두 행동 확정

- 키 홀드로 다음 선택까지 자동 확정

- 연출 중 입력이 다음 상태로 누적

- 메뉴 취소가 전투 행동 취소로 오작동

- 포커스 이동만으로 행동 확정

입력 버퍼를 사용한다면 허용되는 상태와 소비 시점을 명확히 정의한다.

---

# 18. Game Feel과 Juice

전술 게임의 손맛은 실시간 QTE를 덧붙이는 것이 아니라 **내 선택의 결과가 정확한 타이밍과 재질감으로 돌아오는 것**에서 만든다.

다음 흐름이 좋게 느껴져야 한다.

```text

선택

→ 준비

→ 긴장

→ 행동 발동

→ 접촉 또는 결과

→ 반동

→ 다음 판단

```

연출 방법은 자유롭게 결정한다.

사용 가능한 수단:

- anticipation

- 빠른 contact frame

- recoil

- hit-stop

- directional shake

- sprite flash

- squash/stretch

- trail

- debris

- particles

- damage popup

- sound layering

- pitch variation

- brief zoom

- environment reaction

모든 효과를 사용할 필요는 없다.

## 무기별 차이

빠른 무기는 **즉각적이고 정밀하게** 느껴져야 한다.

무거운 무기는 **준비와 접촉의 대비**로 무게를 느끼게 한다.

방패는 선택할 때의 자세와 실제 피격 접촉이 모두 읽혀야 한다.

마법이나 특수 공격은 물리 공격과 다른 재질감을 가진다.

회복은 공격 효과처럼 보이지 않게 한다.

같은 애니메이션을 속도와 색만 바꿔 모든 행동에 재사용하지 않는다.

---

# 19. 피드백 강도

다음 결과는 서로 다른 피드백을 가져야 한다.

- 일반 피해

- 큰 피해

- 완전 방어

- 약한 방어

- 회복

- 행동 지연

- 처치

- 플레이어 패배

피해 0인데 큰 붉은 피격 연출을 재생하지 않는다.

완전 방어도 아무 반응 없이 숫자 0만 표시하지 않는다.

HP 변화, 피해 숫자, 접촉 효과, 사운드는 같은 사건을 나타내야 한다.

매 공격마다 전체 화면 섬광, 긴 슬로모션, 큰 화면 흔들림을 사용하지 않는다.

강한 사건에 더 큰 표현 예산을 사용한다.

HUD 전체는 불필요하게 흔들지 않는다.

---

# 20. 연출과 판정 분리

논리 전투가 게임의 권위 상태다.

애니메이션, 사운드, 카메라, 파티클은 확정된 전투 사건을 표현한다.

다음을 금지한다.

- 애니메이션 이벤트가 피해량을 새로 계산

- 물리 충돌 여부로 이미 확정된 공격 취소

- 프레임 드롭으로 Wait 변경

- hit-stop으로 logicalTime 변경

- 연출 스킵으로 행동 순서 변경

- 사운드 종료 시점으로 다음 행동 결정

연출 속도, 사운드 설정, 화면 흔들림 감소, 애니메이션 스킵이 달라도 같은 선택은 같은 전투 결과를 내야 한다.

---

# 21. Pixel Art 품질

단순히 작은 해상도나 nearest-neighbor 필터를 사용했다고 Pixel Art 완성으로 간주하지 않는다.

형태, 실루엣, pixel cluster, 색, 명암, 재질 표현을 의도적으로 설계한다.

해상도, 팔레트 수, outline, 애니메이션 frame 수는 게임에 맞게 정한다.

실제 표시 크기에서 먼저 읽혀야 하는 것은 다음이다.

- 캐릭터 실루엣

- 현재 들고 있는 장비

- 공격 방향

- 적의 준비 자세

- 위험 행동

- 접촉 순간

애니메이션에서는 다음을 확인한다.

- anchor 흔들림

- 프레임별 크기 변화

- 무기 위치 튐

- 팔다리 변형

- texture flicker

- 고립 픽셀

- 색 오염

- 불필요한 jaggies

- 투명 경계 halo

카메라 이동과 화면 크기 변경에서도 픽셀이 뜻하지 않게 번지거나 떨리지 않게 한다.

임시 사각형, 이모지, 텍스트 기호를 최종 캐릭터·무기·적 아트 대신 남기지 않는다.

---

# 22. 기술 기본안

기존 실행 가능한 프로젝트가 제공되었다면 그 프로젝트의 기술 스택과 구조를 우선한다.

새 브라우저 게임을 처음 만드는 경우 기본안은 다음이다.

```text

TypeScript

Phaser

Vite

```

Windows 11의 최신 데스크톱 브라우저에서 실행 가능하게 한다.

필요 없는 백엔드, 계정, 온라인 서비스, 데이터베이스는 만들지 않는다.

전투 규칙은 Phaser Scene이나 Sprite 객체 안에 직접 섞지 않는다.

권장 경계:

```text

Combat Simulation

    ↓ events

Presentation / Animation / Audio

Input

    ↓ commands

Combat Simulation

Save Data

    ← serializable game state

```

전투 시뮬레이션은 렌더링 없이도 테스트 가능하게 한다.

과도한 인터페이스, 전역 Manager, 범용 Event Bus는 필요하지 않다.

# 24. 필수 전투 검증

구현한 전투 규칙에는 최소한 다음 상황을 검증한다.

정확한 테스트 코드 구조는 자유다.

### 남은 시간 보존

```text

Player Wait 3

Enemy Wait 10

```

플레이어 행동 후 적 남은 Wait가 7이어야 한다.

### 느린 플레이어 행동

```text

Player Wait 10

Enemy Wait 3

Enemy next Wait 4

```

적 첫 행동 후 플레이어 7.

적 두 번째 행동 후 플레이어 3.

플레이어 행동을 임의로 다시 선택할 수 없어야 한다.

### 준비 중 방어

```text

Enemy physical Effect 18

Player Shield Defense 14

```

방패 준비 중 공격을 받으면 기본 피해는 4다.

### 방패 종료 후 교체

방패 행동이 끝난 뒤 Defense 0인 공격 행동을 고르면 그 순간부터 이전 Defense 14는 사라져야 한다.

### 방어 무시

Defense 14인 상태에서도 방어 무시 Effect 18은 기본 피해 18이다.

### 동률 처치

양측 Wait가 함께 0이고 플레이어 선행 공격으로 적 HP가 0이 되면 적 행동은 실행되지 않는다.

### 동률 후 방패

양측 Wait가 함께 0이고 플레이어 공격 후 적이 생존한다.

다음 행동으로 Defense 14 방패를 선택하면, 이미 Wait 0인 적 Effect 18 공격을 추가 시간 없이 받고 피해는 4다.

새 방패 Wait는 이 공격 때문에 감소하지 않는다.

### 연출 독립성

사운드, 화면 흔들림, 연출 속도, 스킵 옵션이 달라도 논리 시간, HP, 행동 순서, 승패가 같아야 한다.

### 미리보기 순수성

hover, 포커스 이동, 설명 열람, 취소가 HP, Wait, Defense, Buff, 소모 자원에 영향을 주지 않아야 한다.

### 중복 입력

더블 클릭, 연타, 키 홀드, 재시작 연타가 행동·보상·아이템을 중복 처리하지 않아야 한다.

# 25. 밸런스 검증

각 일반 적과 보스에 대해 적어도 하나의 실제 승리 가능한 전략을 확인한다.

하지만 하나의 정답만 존재하도록 만들 필요는 없다.

반대로 모든 적에게 같은 장비 하나만 반복해도 쉽게 승리한다면 장비 선택 시스템이 실패한 것이다.

다음 정책을 비교해 보라.

```text

항상 가장 높은 Effect 장비 사용

항상 가장 짧은 Wait 장비 사용

항상 가장 높은 Defense 장비 사용

상대 행동을 보고 장비를 바꾸는 전략

```

마지막 전략이 상황에 따라 실제 이점을 가져야 한다.

숫자상 승리 가능하다는 것과 플레이했을 때 재미있다는 것은 별도로 판단한다.

# 26. 실제 플레이 검증

Build 성공만으로 완료하지 않는다.

실제 runtime에서 다음 흐름을 직접 확인한다.

```text

실행

→ 타이틀 또는 시작

→ 첫 조작 이해

→ 탐험

→ 첫 장비 획득

→ 전투

→ 패배 또는 승리

→ 재도전

→ 성장 또는 장비 변경

→ 여러 전투

→ 보스

→ 엔딩

```

추가로 확인한다.

- 콘솔 오류

- 누락 에셋

- 저장·이어하기

- 재시작

- 한글 표시

- 창 크기 변경

- 키보드·마우스

- 오디오 중복

- 이전 전투 callback 잔존

- 보상 중복

- UI 잘림

- Pixel Art 떨림

- 접촉 위치

- 피해 숫자와 HP 변화 동기

- 방패 피격 피드백

- 반복 전투의 연출 피로도

발견한 진행 불가와 명백한 품질 결함은 수정한다.

이미 충분히 확인한 검사를 의미 없이 반복하지 않는다.

# 27. 완료 기준

다음이 모두 충족되어야 완료다.

- 게임이 실제로 실행된다.

- 외부 설명 없이 첫 플레이를 시작할 수 있다.

- 장비 선택과 Wait가 전투 결과를 실제로 바꾼다.

- Defense 전환이 실제 판정과 UI에 일치한다.

- 적 행동을 읽고 대응할 수 있다.

- 빠른 장비와 느린 장비의 사용감이 다르다.

- 공격과 방어에 손맛이 있다.

- 탐험과 전투가 실제 진행으로 연결된다.

- 새로운 장비 또는 성장이 플레이 방식을 확장한다.

- 패배 후 다시 도전할 수 있다.

- 최종 도전과 결말이 존재한다.

- 임시 placeholder가 최종 핵심 화면에 남지 않는다.

- 핵심 전투 테스트가 통과한다.

- 실제 플레이 흐름을 끝까지 검증했다.

- 알려진 치명적 진행 불가 문제가 없다.

# 28. 작업 지속 규칙

단계 하나를 끝냈다는 이유로 작업을 멈추지 않는다.

다음 단계가 현재 권한과 환경에서 실행 가능하면 계속 진행한다.

다음과 같은 보고만 남기고 종료하지 않는다.

- “기본 구조를 만들었습니다.”

- “다음은 전투 구현입니다.”

- “테스트를 추가하면 됩니다.”

- “아트는 추후 개선 가능합니다.”

현재 턴에서 가능한 구현, 실행, 테스트, 수정, polish를 실제로 수행한다.

다음 경우에만 사용자 입력을 기다린다.

- 핵심 규칙에 서로 양립할 수 없는 두 사용자 의도가 존재

- 필요한 파일이나 권한이 실제로 없음

- 외부 서비스 인증이 필요

- 파괴적이거나 승인 필요한 작업이 필요

- 이 문서로 결정할 수 없는 핵심 제품 선택이 있음

그 외에는 합리적인 결정을 내리고 계속한다.
